## 阶段零：先定边界，再写第一行代码（第 1–3 天）

知识库失败最常见的原因，不是模型不够强，而是一开始就想做“全公司知识库”。正确的起点是选一个**高频、知识边界清晰、答错代价可控的窄场景**——内部 IT 问答、产品手册问答、某个业务线的制度查询，而不是一上来就覆盖所有文档。

### 核心工作

1. **场景定义文档**：明确知识库“不做什么”。哪些问题应该被拒答、哪些文档不允许入库、用户看到答案的权限边界在哪里，需要在写代码之前就定下来。
2. **数据敏感度与部署底线**：如果文档涉及薪酬、源码、财务，必须走全私有化部署；如果不敏感，云端 API + 开源 RAG 框架可以显著缩短起步时间。
3. **第一版黄金测试集雏形**：从业务方收集 30–50 个真实高频问题，人工标注“标准答案应该命中哪份文档的哪个片段”。这份集合会在后续每个阶段被反复使用，**它的质量直接决定评测的可信度**。

### 产出物

- 场景边界文档（签字确认）
- 部署方案与数据敏感度说明
- 黄金测试集初版：覆盖至少 30 条真实问题，每条包含：
  - `question`
  - `ground_truth`
  - `expected_chunk_id`（预期命中的切片 ID）

### 验收标准

- 场景边界文档签字确认
- 黄金测试集覆盖至少 30 条真实问题，且每条都有三个字段

## 阶段一：把数据做“干净”，而不是急着向量化（第 4–7 天）

行业里有一句被反复验证的话：**Garbage in, garbage out**。检索质量的上限由数据质量决定，而不是由向量库或大模型决定。

### 核心工作

#### 1. 文档解析

- 扫描件必须做 OCR，否则相关内容在检索中等于不存在。
- 表格是最大的陷阱：一个三列表格如果被固定长度切分从中间截断，上下两半单独看语义都不突出，向量化后得分极低，永远不会被召回——这正是真实故障中“知识库明明有答案却答错”的典型根源。
- 表格应整块保留，必要时转化为问答对或平铺叙述。

#### 2. 清洗与去重

- 去除页眉页脚、乱码、过期版本。
- 企业文档库中同一制度往往存在多个版本，旧版本如果不剔除，会持续污染检索结果。

#### 3. 语义切分

- 放弃“固定 500 字切一刀”的做法。
- **按语义单元切分**：Markdown 按标题层级，PDF 按章节，表格整块保留，代码和结构化内容单独切并加类型前缀。
- 单块控制在 500–800 token，重叠 10%–15%，避免边界截断。
- 每个 chunk 必须保留**来源文档、页码、章节、版本、权限范围**等元数据，这些字段在后续的检索过滤和引用溯源中不可替代。

### 产出物

- 一份可复现的文档处理流水线（解析 → 清洗 → 切分 → 元数据标注）
- 第一版入库 chunk 列表

### 验收标准

- 黄金测试集中 80% 以上的 `expected_chunk_id` 存在于切分结果中
- 抽查 20 个 chunk，每个都能追溯到明确的来源页码和章节

## 阶段二：搭建检索基座——召回优先，精排提纯（第 8–15 天）

这是技术投入最集中的阶段。检索链路的设计原则是：**混合检索保证召回率，Rerank 保证首屏精度，小上下文控制成本和幻觉**。

### 核心工作

#### 1. 向量库选型，但不要过度选型

- 百万级 chunk 以内、已有 PostgreSQL 的团队，**pgvector** 是零新增组件的最经济起点。
- 百万到千万级且对延迟敏感，**Qdrant** 单机部署更简单；**Milvus** 生态更全。
- 一个反直觉但重要的判断：**绝大多数团队在换向量库之前，应该先换 embedding 模型和检索策略**——召回率的天花板由 embedding 质量决定，而不是向量库。

#### 2. 混合检索是必选项

- 纯向量检索对专有名词、型号、API 名、缩写词的召回很差，因为这类词在语义空间中容易漂移。
- 标准做法：向量检索与 BM25 关键词检索并行召回，各取 Top 30–50，然后用 **RRF（倒数排名融合）** 对齐两路结果。
- RRF 不依赖各引擎的原生分数，而是按排序位置做无偏融合，常数 k 通常取 60。
- 参考实测数据：混合检索 + rerank 相比纯向量，在售后知识库上 Recall@5 从 0.71 提升到 0.92，问答准确率从 68% 提升到 84%，改造成本约一周。

#### 3. Rerank 负责把“召回”变成“可用”

- 向量检索基于双塔模型独立编码，缺乏 Query 与文档之间的细粒度交叉注意力；BM25 和向量分数的量纲也不一致。
- 将 RRF 融合后的 Top 20–30 候选逐一与 Query 配对送入 Cross-Encoder Rerank 模型（中文场景可用 bge-reranker 或 GTE-Rerank）。
- 输出绝对相关性分数，再用阈值截断（如 Score < 0.35 丢弃）和 Top 5–8 截取，得到真正进入 Prompt 的高纯度上下文。

#### 4. 查询侧优化作为兜底

- 查询改写、同义词扩展、HyDE 可以按需加入。
- 但不要在检索基线跑通之前过早引入复杂度。

### 产出物

- 可通过 API 调用的检索服务：输入问题，输出带分数、来源元数据的 Top-N 片段
- 检索层 Recall@K 评测脚本

### 验收标准

- 在黄金测试集上，**Recall@5 ≥ 0.90**
- 如果低于该阈值，优先回头检查切分策略和 embedding 模型，而不是换向量库

## 阶段三：生成约束与 Agent 编排——从“固定流水线”到“按需检索”（第 16–22 天）

检索基座就绪后，先做一个**最小可用的固定流水线**：检索 → 拼装 Prompt → 生成带引用的答案。这一步的意义是建立生成层的质量基线，再在此基础上引入 Agent 编排。

### 核心工作

#### 1. 生成层的硬约束

写入 System Prompt：

- 严格基于提供的参考文档回答
- 资料不足时明确说“知识库中暂未收录”
- 不允许凭模型自身知识发挥
- Temperature 调到 0.1–0.3，降低发散性

引用溯源不是 UI 层的装饰，而应作为答案数据结构的一部分返回：

```json
{
  "answer": "...",
  "evidence": ["..."],
  "citations": [
    {
      "documentId": "...",
      "page": 12,
      "section": "3.2"
    }
  ]
}
