你看到的内容：

```python
content='' additional_kwargs={'reasoning_content': '我们需要'} response_metadata={'model_provider': 'deepseek'} id='lc_run--01a1c9ea-aed1-71e6-98b2-523f9119a549' tool_calls=[] invalid_tool_calls=[] tool_call_chunks=[]
```

它通常是 LangChain 中消息对象（例如 `AIMessage`）的字符串表示。它不是模型原始文本，而是把消息正文、额外参数、响应元数据、工具调用信息等字段一起展示出来。

## 1. 字段总览

| 字段 | 当前值 | 含义 |
|---|---|---|
| `content` | `''` | 消息正文。这里为空字符串，表示正文部分没有内容。 |
| `additional_kwargs` | `{'reasoning_content': '我们需要'}` | 提供商或模型适配器附加的字段，通常不是 LangChain 统一定义的核心消息字段。 |
| `response_metadata` | `{'model_provider': 'deepseek'}` | 关于模型响应的元数据，例如提供商、模型名称、结束原因、 token 使用量等，具体取决于模型和适配器。 |
| `id` | `lc_run--...` | 消息 ID，用于标识这条消息。具体格式由运行环境或适配器生成。 |
| `tool_calls` | `[]` | 已解析成功的工具调用列表。空列表表示当前消息没有可用的已解析工具调用。 |
| `invalid_tool_calls` | `[]` | 无法解析或格式不正确的工具调用列表。空列表表示没有记录到此类调用。 |
| `tool_call_chunks` | `[]` | 流式输出过程中收到的工具调用片段。空列表表示当前对象没有工具调用片段。 |

## 2. 重点字段详解

### `content`

消息的主要内容，类型通常可以是字符串，也可能是多模态内容块。

```python
AIMessage(content="你好")
```

常见情况：

- 普通文本回答：`content` 保存回答文本。
- 图片、音频等多模态消息：可能保存内容块列表，而不只是字符串。
- 当前示例：`content=''`，正文为空。

**注意：正文为空不代表模型完全没有返回任何信息。** 其他字段仍可能包含推理内容、工具调用或元数据。

### `additional_kwargs`

附加参数字典，用来承载模型提供商特有、LangChain 通用消息结构暂时无法统一表达的信息。

当前示例：

```python
additional_kwargs={
    "reasoning_content": "我们需要"
}
```

这里的 `reasoning_content` 是 DeepSeek 适配过程中携带的推理内容字段。

需要注意：

- 它不是所有模型都支持的统一字段。
- 不同模型提供商可能使用不同字段名。
- 它可能是流式生成中的一个片段，也可能是完整内容，取决于调用方式和适配器。
- 不应默认把它当作普通面向用户的回答正文。

### `response_metadata`

响应元数据字典，描述模型这次响应的附加信息。

当前示例：

```python
response_metadata={
    "model_provider": "deepseek"
}
```

它可能包含以下信息（是否存在取决于模型和适配器）：

| 常见键 | 含义 |
|---|---|
| `model_provider` | 模型提供商，例如 DeepSeek、OpenAI。 |
| `model_name` | 实际使用的模型名称。 |
| `finish_reason` | 模型结束生成的原因，例如正常结束或达到长度限制。 |
| `token_usage` / `usage` | 输入、输出及总 token 用量。 |
| `system_fingerprint` | 某些提供商返回的系统或模型版本标识。 |

这些只是常见示例，并不代表每个模型都会返回这些键。

### `id`

消息的唯一标识符或运行时生成的标识符。

当前值：

```text
lc_run--01a1c9ea-aed1-71e6-98b2-523f9119a549
```

通常可用于日志关联、追踪消息或调试。不要依赖它的具体前缀和格式作为业务逻辑判断条件。

### `tool_calls`

模型请求调用工具时，经过解析后的结构化调用列表。

例如：

```python
AIMessage(
    content="",
    tool_calls=[
        {
            "name": "get_weather",
            "args": {"city": "上海"},
            "id": "call_123",
            "type": "tool_call"
        }
    ]
)
```

这表示模型提出了调用 `get_weather` 工具的请求。**它不等于工具已经执行成功**，通常还需要由 Agent 或 LangGraph 执行对应工具，并把工具结果作为 `ToolMessage` 返回给模型。

当前 `tool_calls=[]`，表示这条消息没有已解析的工具调用。

### `invalid_tool_calls`

模型输出了类似工具调用的内容，但 LangChain 无法将其解析为合法工具调用时，相关信息可能出现在这里。

例如模型生成的参数不是合法 JSON，或工具调用结构不符合预期。

当前为空，表示没有记录到解析失败的工具调用。

### `tool_call_chunks`

在流式（streaming）输出场景中，工具调用可能分多段到达。LangChain 可以先保存这些片段，后续再合并、解析。

例如一次工具调用可能分批收到：

```text
片段 1：工具名称的一部分
片段 2：参数 JSON 的一部分
片段 3：剩余参数内容
```

当前为空，表示这条消息对象中没有工具调用流式片段。

## 3. 为什么 `content` 为空，但 `reasoning_content` 有值？

这是当前示例最值得关注的地方：

```python
content = ""
additional_kwargs = {
    "reasoning_content": "我们需要"
}
```

可以理解为：模型适配器把这段内容放在了额外字段 `reasoning_content` 中，而不是放在标准消息正文 `content` 中。

在 DeepSeek 等支持推理内容的模型调用中，推理内容和最终回答可能被分别处理。具体字段位置和行为取决于模型接口、LangChain 集成包以及是否使用流式调用。

另外，`"我们需要"` 只有几个字，很可能只是流式输出中的一个片段，不能仅凭这一条消息就认定它是完整推理内容。

## 4. 在代码中如何读取？

```python
# 标准正文
print(message.content)

# 模型提供商附加字段
print(message.additional_kwargs)

# 单独读取推理内容（如果适配器提供）
reasoning = message.additional_kwargs.get("reasoning_content", "")

# 响应元数据
print(message.response_metadata)

# 已解析的工具调用
for tool_call in message.tool_calls:
    print(tool_call["name"])
    print(tool_call["args"])

# 解析失败的工具调用
print(message.invalid_tool_calls)

# 流式工具调用片段
print(message.tool_call_chunks)
```

如果希望兼容不同模型，不要假设 `reasoning_content` 一定存在：

```python
reasoning = message.additional_kwargs.get("reasoning_content")
if reasoning:
    print("模型推理内容：", reasoning)

if message.content:
    print("模型回答：", message.content)
```

## 5. 在 LangGraph 中应该关注什么？

LangGraph 的消息状态通常会保存多种消息对象，例如：

- `HumanMessage`：用户输入。
- `AIMessage`：模型输出，可能包含正文、附加字段或工具调用。
- `ToolMessage`：工具执行后的结果。

一个典型工具调用流程：

```text
HumanMessage
    │
    ▼
AIMessage（tool_calls 中包含工具调用请求）
    │
    ▼
执行工具
    │
    ▼
ToolMessage（保存工具执行结果）
    │
    ▼
AIMessage（模型根据工具结果生成回答）
```

因此，判断模型是否请求调用工具，优先检查：

```python
if message.tool_calls:
    # 交给工具执行逻辑处理
    ...
else:
    # 没有已解析的工具调用
    ...
```

不要仅凭 `content` 是否为空判断是否需要执行工具，因为模型消息也可能通过 `tool_calls` 承载动作请求。

## 6. 一句话记忆

| 字段 | 可以把它理解成 |
|---|---|
| `content` | 模型的正文 |
| `additional_kwargs` | 模型提供商额外塞进来的信息 |
| `response_metadata` | 本次响应的说明信息 |
| `id` | 这条消息的标识 |
| `tool_calls` | 模型提出的工具调用请求 |
| `invalid_tool_calls` | 没能正确解析的工具调用 |
| `tool_call_chunks` | 流式传输中的工具调用碎片 |

**对你这条具体数据的结论：** 这是一条带有 DeepSeek 提供商元数据的消息对象；正文 `content` 为空，附加字段中有 `reasoning_content='我们需要'`，没有已解析的工具调用，也没有无效工具调用或工具调用片段。
