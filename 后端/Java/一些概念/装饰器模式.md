思想 不改原类, 动态给它"套一层", 一层套一层累积增强 —— 组合优于继承

## 定义与角色

| 角色 | 职责 | 例子 |
|---|---|---|
| Component (抽象) | 统一接口 | InputStream |
| ConcreteComponent (被装饰者) | 真正干活 | FileInputStream |
| Decorator (装饰器基类) | 持有 Component 引用, 接口透传 | FilterInputStream |
| ConcreteDecorator (具体装饰器) | 附加新职责 | BufferedInputStream |

关键: 装饰器和被装饰者**实现同一接口**, 装饰器内部再调被装饰者, 因此可以无限嵌套。

## Java 最经典案例: IO 流

```java
InputStream in = new BufferedInputStream(new FileInputStream("a.txt"));
// 1MB 后加解密, 再压一层: new GZIPInputStream(buffered)
```

每一层只做一件事, 自由组合。Spring 里装饰器模式用得很少 (Spring 更爱用代理模式), 找装饰器就找 Java IO。

## 与代理模式对比

| 维度 | 装饰器 | 代理 |
|---|---|---|
| 目的 | 增强功能 | 控制访问 (权限/延迟加载/日志) |
| 接口关系 | 与被装饰者同接口, 客户端不感知 | 代理可能不暴露真实接口 |
| 创建者 | 客户端手动嵌套 | 容器/框架生成 (如 Spring AOP) |
| 典型 | BufferedInputStream | Spring AOP 代理、RMI、虚拟代理 |

一句话: 装饰器"叠加能力", 代理"拦截行为"。

## 和"装饰器/注解"一词的关系

JS/TS 里 @Decorator、Spring 的 @Service 也叫"装饰器", 但那本质是**注解/元编程**, 由框架解释执行; GoF 装饰器是**运行时对象包装**。两者同名不同物, 别混。
